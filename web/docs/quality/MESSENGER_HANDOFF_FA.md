# بررسی و تحویل پیام‌رسان ماکان

نسخهٔ بررسی: ۱ نوامبر۲۰۲۶ — کلاینت Next.js/React در پوشهٔ `web/`، سرور تست `http://94.184.32.84:8090`.

## تغییرات قابل بررسی

1. یک فهرست پیام برای هر حساب؛ کلید «شخصی / آموزشگاه» حذف شده است. گفتگوهای حساب و سازمان فعال در همان فهرست می‌آیند. نشان رسمی و مجوز خواندن حفظ می‌شوند.
2. ایجاد گروه و کانال در دو مرحله: اطلاعات، سپس مخاطبین. بازگشت، جستجوی مخاطب، صفحه‌بندی، reload و حفظ پیش‌نویس پشتیبانی می‌شوند. ایجاد فقط با تأیید نهایی است.
3. مدیریت گفتگو با ردیف‌های آیکن‌دار، صفحهٔ مستقل ویرایش نام/توضیح، افزودن عضو، ارتقا/تنزل مدیر و حذف عضو با تأیید. خطا بسته یا موفق نمایش داده نمی‌شود.
4. فرم‌ها و پاپ‌آپ‌ها در حالت روشن/تاریک و اندازه‌های۳۹۰،۸۳۴ و۱۴۴۰ بررسی می‌شوند؛ تصاویر واقعی در `output/review/messenger-management/` هستند.

## مانع واقعی سرور تست

ورود چهار حساب و۱۲حالت حساب/اندازه روی Docker موفق بود. اما هر چهار حساب `VerificationRequired` و فقط مجوز خواندن گفتگوهای موجود/کشف افراد مرتبط دارند؛ ساخت گروه/کانال در allowedActions نیست. یک درخواست مشخص ساخت گروه با عضو اولیهٔ Teacher با409 و `CONVERSATION_INVITATION_REQUIRED` رد شد. **ساخت تازه و mutation مدیریت سرور در این نوبت تأیید نشدند. ارسال در گفتگوی مستقیمِ موجود مستقل بررسی و موفق شد:** پیام Student بدون reload در فهرست Teacher ظاهر شد و پاسخ Teacher به چت باز Student رسید. در دو تکرار موفق، مجموع چهار پیام آزمایشی در گفتگوی مجاز همین دو حساب باقی ماندند. صفحهٔ اطلاعات گروه موجود هم با API واقعی بررسی شد. درخواست آماده‌سازی حساب‌ها و شواهد دقیق در G21.4 است. ابزار دستی پس از ثبت این شاهد، پیش‌شرط مجوز را بررسی و نوشتن را تا آماده‌شدن حساب متوقف می‌کند.

## مرز اتصال

عملیات info/members/member-role از قرارداد واقعی به کلاینت اضافه شده‌اند. schema عملیات با OpenAPI زنده برابر است. آزمون مرورگر مستقل از سرور واقعی اجرا می‌شود. ابزار دستی `scripts/review-messenger-management.mjs` خارج از CI و با opt-in، حساب‌های تست معرفی‌شده را روی Docker بررسی می‌کند؛ فقط گروه/کانال QA اختصاصی می‌سازد، ویرایش/پیام/عضویت را در همان‌ها آزمایش می‌کند و آثار ایجادشده را برای مالک آرشیو می‌کند. حساب‌ها یا گروه‌های دیگر تغییر نمی‌کنند. نتیجه و محدودیت واقعی در `MESSENGER_MANAGEMENT_LIVE.json` ثبت می‌شود.

## موارد قابل تحویل به بک‌اند

شرح کامل در بخش G21 فایل `docs/API_GAPS.md`:

- صندوق یکپارچهٔ واقعی با مرتب‌سازی، جستجو و cursor سراسری؛ API فعلی scopeهای جدا دارد. ادغام صفحات بارگذاری‌شدهٔ کلاینت معادل پوشش تمام سازمان‌ها یا ترتیب سراسری قطعی نیست.
- مجوز مؤثر مدیر/عضو و کاتالوگ ماشین‌خوان permission؛ رشته‌های opaque فعلی برای ساخت تنظیمات جزئی کافی نیستند. فعلاً کنترل‌ها برای Owner فعالِ UserManaged در دسترس‌اند.
- عکس گروه/کانال و شناسه/لینک عمومی با قرارداد معتبر؛ از endpoint عکس حساب یا لینک حدسی استفاده نشده است.
- رفتار تکرار افزودن عضو، محدودیت حریم خصوصی، مالکیت و لغو دسترسی با خطاهای مشخص و بررسی سمت سرور.

دعوت‌نامه، لینک دعوت و انتقال مالکیت API موجود دارند؛ این‌ها «بک‌اند ندارد» گزارش نشده‌اند، ولی رابط کاملشان در دامنهٔ این مرحله آماده معرفی نمی‌شود.

## نتیجهٔ بررسی محلی

۲۶۶تست واحد در۴۹فایل موفق شد. مجموعهٔ کامل۱۱۷سناریویی پیش از افزودن تست رضایت موفق بود. اجرای کامل۱۱۸سناریویی پس از آن۱۱۷موفق و۱خطای selector خودِ تست داشت؛ پس از محدودکردن selector به محتوای صفحه، هر۱۴تست هدفمند نهایی موفق شدند. کد برنامه بین اجرای کامل آخر و تکرار هدفمند تغییر نکرد. تعداد۱۱۸سناریوی متمایز، حاصل این اجراهاست و یک اجرای کاملِ۱۱۸/۱۱۸ ادعا نمی‌شود. جزئیات دقیق در گزارش JSON است.

## اجرای بررسی‌ها

از پوشهٔ `web/`:

```sh
npm test
npm run lint
npm run typecheck
npm run generated:check
npm run build -- --webpack
npm run test:browser
```

بررسی هدفمند: `npm run test:browser -- messenger-management.spec.ts conversation-pages.spec.ts`.

رسید نهایی فرمان‌ها و تعداد موفق/ناموفق/اجرانشده در `docs/quality/MESSENGER_MANAGEMENT_CHECKS.json` و وضعیت مرحله در `docs/PROGRESS.md` است. نتیجهٔ تست کلاینت، تأیید امنیت تمام سرور یا آمادگی انتشار کل محصول نیست.
